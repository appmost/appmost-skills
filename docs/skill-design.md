# Why these skills contain this guidance

The highest-value knowledge changes an agent's decisions and can be verified in the app it creates. This package prioritizes six recurring decisions:

| Decision | What the skill contributes | Evidence |
| --- | --- | --- |
| What to build | Identify the app's main task, complete flow and content states. | Coherent navigation and useful real content. |
| Which primitive to choose | Discover supported templates and prefer suitable native controls. | Current contract plus actual behavior. |
| How to compose | Fit type, imagery, surfaces and density to the subject. | Readable full-page renders with a recognizable purpose. |
| How geometry works | Account for native chrome, template/parent insets and natural height. | Actual content frames and reviewed images. |
| How to iterate | Make guarded source changes and re-render in a stable context. | Preserved source and verified affected content. |
| What may be claimed/delivered | Separate source, preview, test, build and current provider evidence. | Exact relevant receipts and honest limits. |

Liquid Glass, modal X buttons and tabbar insets are examples of these decisions. They belong because they prevent concrete native/composition mistakes, not because the package should collect every UI opinion.

## Content placement

- SKILL.md: activation scope, essential workflow and constraints that apply to most tasks.
- references: focused decisions, component guidance, pitfalls and worked examples loaded only when relevant.
- Runtime MCP: exact schemas, catalogs, supported enums and changing host capabilities.
- Official documentation: changing platform/store requirements, fetched when a task needs them.
- Private project process: personal/customer observations, raw evidence and deciding what may become a reusable public rule.
- Appmost product code: renderer or tool defects that instructions cannot fix.

Keep entrypoints far below the 500-line guideline; the current package uses short entrypoints and routes detail. Split a skill when a task has a genuinely different trigger, authority boundary or outcome. File size alone does not justify another skill or a router.

Use the evaluation workflow to test changes. More guidance is useful only when it improves observable choices or output. A long checklist that is never applied is not progress.
