# Why these skills contain this guidance

The highest-value knowledge changes an agent's decisions and can be verified in the app it creates. This package prioritizes six recurring decisions:

| Decision | What the skill contributes | Evidence |
| --- | --- | --- |
| What to build | Identify the app's main task, complete flow and content states. | Coherent navigation and useful real content. |
| Which primitive to choose | Discover supported templates and prefer suitable native controls. | Current contract plus actual behavior. |
| How to compose | Fit type, imagery, surfaces and density to the subject. | Readable full-page renders with a recognizable purpose. |
| How geometry works | Account for native chrome, template/parent insets and natural height. | Actual content frames and reviewed images. |
| How to iterate | Make guarded source changes and re-render in a stable context. | Preserved source and verified affected content. |
| What may be claimed/delivered | Separate source, preview, test, build and current provider evidence. | Exact relevant receipts and honest limits. |

Liquid Glass, modal X buttons and tabbar insets are examples of these decisions. They belong because they prevent concrete native/composition mistakes, not because the package should collect every UI opinion.

## Where guidance belongs

Choose the owner by the decision the advice changes, then identify which consumers actually make that decision. A useful UX recommendation can need a short adaptation in more than one workflow; it does not need a verbatim copy in every prompt. Keep the complete rationale and exceptions in one maintained reference. A maintainer reference such as this file explains placement; installed skills must carry their own task-critical guidance.

| Kind of guidance | Primary owner | Other consumers and boundary |
| --- | --- | --- |
| One app's flow, icon or feature choice | That app's versioned source and authoring fixtures | Record the user's decision and verify the real route. Do not turn a customer preference or unfinished feature into a universal product limitation. |
| Reusable app-authoring UX choice | A focused installed skill reference | Link it from the relevant workflow/review section. Use a short entrypoint reminder only if it changes most tasks. |
| Skill activation and recurring workflow | SKILL.md and its description | Keep conditional detail in discoverable references; avoid a new skill for one control. |
| Flow planning in app generation | The existing outline/navigation-planning prompt | Decide real destinations, peer tabs and modal/push relationships here using the advertised contract. A page generator must respect the accepted graph. |
| Page or row generation | The smallest existing prompt that owns that output | Include only a compact rule expressible by that DTO. It can omit a misleading optional icon or choose an honest action; it must not invent destinations, fields or a new planning stage. |
| Layout-only review or auto layout | The existing geometric layout workflow | Preserve actions, destinations and presentation. A flow correction belongs in a separate authorized authoring operation. Arranging nodes on a page graph does not change app UX. |
| Exact technical constraints and supported values | Current MCP schema/catalog/runtime contract | Use executable validation for objectively invalid states. A contextual design preference is not automatically a schema error or a blanket rewrite. |
| Broken renderer, export or MCP behavior | Product code with a reproducer and affected checks | Do not preserve a temporary workaround as permanent skill advice after its underlying bug is fixed. |
| Permissions, repository process and personal preferences | The applicable project/process instructions | Keep authority local and explicit; a prompt or skill never grants deployment, spending or destructive permissions. |
| Release evidence and provider requirements | Release workflow plus current official documentation | Verify the exact delivery and provider state; avoid copying changing policy manuals into prompts. |
| Customer observations and unresolved hypotheses | Private task journal/issue | Generalize only a verified, lasting lesson. Keep raw captures, account IDs, secrets and internal implementation details out of reusable packages. |

### Example: a top-bar utility

The reusable recommendation belongs in [navigation and data](../skills/appmost/references/navigation-data.md#top-bar-actions-and-destinations): prefer a native modal or supported popover for a short, distinct contextual utility, keep real hierarchical details pushed, and make the icon match its destination. A notification bell cannot disguise a Profile-tab shortcut. If no real notification experience exists, omit that optional action.

An outline generator can receive a compact adaptation when it plans destinations: identify a real utility task and choose the existing presentation relationship. A page generator can receive the relevant local constraint: respect that relationship, match the symbol to the action and omit unsupported optional utilities. A layout reviewer keeps the route unchanged and leaves a behavior finding for the authoring workflow. These are different responsibilities, not permission to copy the complete skill into all three prompts.

Do not infer modal presentation solely from the top-bar position. Preserve native Back/Close/commit controls, direct commands, supported menus and intentional labelled cross-links. Apple's [modality guidance](https://developer.apple.com/design/human-interface-guidelines/modality) requires a clear benefit; treat modal preference as a scoped recommendation rather than an Apple requirement for all toolbar items.

### Moving a lesson into instructions

Start with the observed artifact and the source/host context. Separate a confirmed cause, a design recommendation and a user-specific decision. Check whether an existing rule already covers the issue and whether the final product correction makes a proposed workaround obsolete.

Choose the primary owner from the table, list actual consumers and explain why each needs an adaptation or no change. Record the exact source/version, chosen wording, relevant exceptions and validation. Keep proposed, locally changed, reviewed, installed and deployed states distinct. An updated skill does not update a hosted generation prompt; a source commit does not prove its deployment or model behavior.

Validate only what changed. Structural skill checks and package inspection establish installability, not useful navigation choices. For a behavior change, use a realistic case and a nearby exception where feasible; report unexecuted model or interaction checks honestly. Do not claim an independent evaluation for a self-review or introduce a costly new pipeline solely to test a sentence.

Keep entrypoints short. Split a skill when the task has a different trigger, authority boundary or outcome; file size alone does not justify another skill or router. Prefer a link and a small consumer-specific adaptation over copies that drift.

### Example: repeatable spacing review

The Appmost skill owns the workflow for selecting related content and verifying rendered gaps. Its design reference carries role-based starting values and the reusable measurement script reads existing evidence. Layout-only tools should show geometric deviations and propose changes to the spacing owner while preserving controls and navigation. Generator instructions can say to group related text and use content-sized rows, because an initial draft has no measured geometry. Shared policy and evaluation belong here; retain a single executable measurement implementation and verify it on synthetic rendered cases before reusing the rule in a prompt.
